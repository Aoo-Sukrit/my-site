# ฐานข้อมูล Supabase

ไฟล์ SQL ทั้งหมดอยู่ใน `supabase/migrations/` และรันขึ้นฐานข้อมูลจริง
อัตโนมัติผ่าน Supabase GitHub integration

## กฎการเพิ่มไฟล์ใหม่

**ตั้งชื่อ** `YYYYMMDDHHMMSS_ชื่อสั้นๆ.sql` เช่น `20260930120000_add_challenges.sql`
เวลาต้องมากกว่าไฟล์ล่าสุดในโฟลเดอร์เสมอ เพราะ Supabase รันเรียงตามชื่อไฟล์
ถ้าตั้งเวลาย้อนหลังไปก่อนไฟล์ที่รันไปแล้ว ไฟล์นั้นจะถูกข้าม

**ไฟล์ที่ push ไปแล้วห้ามแก้เนื้อใน** ต่อให้เจอว่าเขียนผิด
เพราะฐานข้อมูลจดไว้แล้วว่ารันไฟล์นั้นไปแล้ว แก้ไปก็ไม่มีผล
ถ้าต้องแก้ให้สร้างไฟล์ใหม่ที่เวลาใหม่กว่า แล้วเขียนคำสั่งแก้ในนั้น

**ยังต้องเขียนให้รันซ้ำได้ไม่พัง** ใช้ `if not exists`, `create or replace`,
`drop ... if exists` ก่อน `create` เหมือนเดิม
ไม่ใช่เพราะ Supabase จะรันซ้ำ แต่เพราะตอนพัฒนาเรามักรันเองด้วยมือใน
SQL Editor ก่อน แล้วค่อย push ถ้าไฟล์รันซ้ำไม่ได้จะติดตั้งแต่ตอนนั้น

## พอ push แล้วเกิดอะไรขึ้น

push ขึ้น `main` แล้ว Supabase จะดูว่ามีไฟล์ไหนใน `supabase/migrations/`
ที่ยังไม่ได้จดไว้ในประวัติ แล้วรันเฉพาะไฟล์นั้นตามลำดับเวลา
ไฟล์ที่รันไปแล้วจะถูกข้าม

ถ้าไฟล์ไหนรันแล้ว error การ deploy จะหยุดตรงนั้น ไฟล์ถัดไปจะไม่ถูกรัน
ให้ไปดู log ที่ Supabase Dashboard แล้วแก้ด้วยการสร้างไฟล์ใหม่

## ประวัติ ณ ตอนตั้งค่า

ไฟล์เก้าไฟล์แรก (`20260924000001` ถึง `20260929000009`) ถูกรันด้วยมือ
ใน SQL Editor ไปก่อนแล้ว ตอนตั้งค่าจึงใช้

```
npx supabase migration repair --status applied <เวอร์ชัน...>
```

เพื่อจดว่ารันไปแล้ว คำสั่งนี้แตะแค่ตารางประวัติ ไม่ได้รัน SQL ในไฟล์ซ้ำ
ไฟล์ถัดจากนี้ไปไม่ต้องทำแบบนั้นอีก push แล้วรันเองเลย

## คำสั่งที่ใช้บ่อย

```
npx supabase migration list      ดูว่าฝั่งเครื่องกับฝั่งเซิร์ฟเวอร์ตรงกันไหม
npx supabase migration new ชื่อ   สร้างไฟล์เปล่าพร้อมเวลานำหน้าให้
```

`supabase db push`, `db reset`, `db pull` ไม่ต้องใช้ในงานปกติ
สองตัวแรกเขียนทับฐานข้อมูลจริงได้ ใช้เมื่อรู้แน่ว่ากำลังทำอะไรอยู่เท่านั้น
